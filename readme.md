# ДЗ 3. In-memory LSM: `Range` по всей DB и background compaction


В ДЗ 1 у вас появилась потокобезопасная `Memtable` с упорядоченным `Range()` и `tombstone`. В ДЗ 2 поверх нее появился `DB` с `mutable/immutable memtable`, фоновым `flush` и in-memory `SSTable`. Теперь нужно добавить две ключевые возможности:
- `Range()` уже на уровне **всей DB**, а не только одной `Memtable`
- фоновую **compaction** для in-memory `SSTable`, чтобы база сама поддерживала структуру в рабочем состоянии

В этом ДЗ по-прежнему и **нет персистентности**: все данные только в памяти

## Что нужно реализовать

**DB** — основной объект, который управляет состоянием:
- хранит одну **mutable** memtable
- хранит очередь **immutable** memtable (замороженные, ожидают flush)
- хранит список **SSTable** (in-memory, immutable)
- имеет одного фонового **flusher**-а
- имеет одного фонового **compactor**-а

**SSTable** в этом ДЗ:
- immutable
- внутренняя структура — линейный массив/срез записей, отсортированный по ключу
- каждая запись хранит `key`, `value` и `tombstone`
- поиск по ключу допускается линейный или бинарный

**Options** — параметры:
- `MemtableMaxRecords` — лимит количества уникальных ключей (включая tombstone) в mutable memtable для ротации
- `SSTableCompactThreshold` — порог по количеству SSTable; если таблиц становится слишком много, должна запускаться compaction
- если `MemtableMaxRecords <= 0`, используй `DefaultOptions().MemtableMaxRecords`
- если `SSTableCompactThreshold <= 0`, используй `DefaultOptions().SSTableCompactThreshold`

## Требуемый API

DB должен предоставлять методы:
- `Open(opts Options) *DB`
- `Put(key string, value []byte)`
- `Get(key string) ([]byte, bool)`
- `Delete(key string)`
- `Range(start, end string, fn func(key string, value []byte) bool)`
- `Close()`

Можешь добавлять вспомогательные методы и внутренние структуры, но публичный API должен оставаться минимальным

## Поведение операций

- `Put` записывает значение в текущую mutable memtable.
- `Put` должен сохранять **копию** `value`, чтобы последующие изменения исходного слайса не меняли сохраненное значение.
- `Delete` записывает tombstone в текущую mutable memtable.
- `Get` ищет ключ в порядке от самого нового к старому:
    1. `mutable memtable`
    2. `immutable memtables` (от новых к старым)
    3. `sstables` (от новых к старым)
- Если найден tombstone, ключ считается удаленным и `Get` возвращает `(nil, false)`.
- `Get` должен возвращать **копию** `[]byte`, чтобы внешние изменения не ломали данные.
- Более новая запись всегда перекрывает более старую, независимо от того, в `mutable`, в `immutable` или в `sstable` она находится.

## `Range()` по всей DB

Нужно реализовать `Range(start, end, fn)` для **всей базы**, а не только для одной `Memtable`.

### Семантика `Range`

- `Range` должен обходить только **актуальные** записи по всей DB.
- Порядок ключей в выдаче — **по возрастанию**.
- Каждый ключ должен появляться не более одного раза.
- Для каждого ключа должна использоваться та же логика приоритета, что и в `Get`: более новая запись перекрывает более старую.
- Если для ключа актуальной записью является tombstone, этот ключ **не должен попадать** в `Range`.
- `Range` должен вызывать `fn(key, value)` для каждой видимой записи.
- Если `fn` вернула `false`, обход нужно немедленно прекратить.
- В `fn` нужно передавать **копию** `[]byte`, а не ссылку на внутренние данные.

### Границы диапазона

Используйте полуинтервал:
- `start` — **включительно**
- `end` — **не включительно**

То есть `Range(start, end, fn)` должен обходить ключи `start <= key < end`.

Упрощения:
- если `start == ""`, диапазон не ограничен слева
- если `end == ""`, диапазон не ограничен справа
- если обе границы заданы и `start >= end`, `Range` ничего не возвращает

## Консистентность `Get` и `Range`

Главная идея этого ДЗ — не просто добавить новые методы, а сделать их корректными на фоне параллельных перестроек структуры.

Требования:
- `Get` и `Range` должны работать корректно параллельно с `Put/Delete`, `flush` и `compaction`.
- `Get` и `Range` должны видеть **целостное состояние** базы.
- Допускается, что операция увидит состояние **до** публикации новой `SSTable` или **после** публикации новой `SSTable`, но не «между» этими состояниями.
- Аналогично для compaction: операция может увидеть набор `SSTable` **до** слияния или **после** него, но не частично замененный набор.
- Допускается, что `Range`, начавшийся раньше, не увидит `Put/Delete`, которые стартовали позже. Это нормально, если `Range` работает по консистентному снимку.

## Ротация memtable

- При достижении `MemtableMaxRecords` текущая memtable становится immutable.
- Запись, которая довела `Len()` до лимита, остается в старой (ставшей immutable) memtable; ротация происходит **после** вставки.
- Создается новая mutable memtable.
- Immutable memtable отправляется в очередь `flush`-горутине.
- Пока соответствующая `SSTable` не будет полностью построена и опубликована в списке `sstables`, старая immutable memtable должна оставаться видимой для `Get` и `Range`.

## Фоновый flush

- Flush выполняется **одной** фоновой горутиной.
- Фоновая горутина читает immutable memtable из буферизированного канала и строит из нее новую in-memory `SSTable`.
- Порядок обработки immutable memtable должен быть **FIFO**.
- Для `Get` и `Range` immutable memtable и `SSTable` должны просматриваться от новых к старым, независимо от FIFO-порядка `flush`.
- `Put/Delete` не должны ждать `flush`; для этого канал очереди должен быть буферизированным.
- После успешного `flush` новая `SSTable` добавляется в список `sstables`, а соответствующая immutable memtable удаляется из списка видимых immutable memtable.
- Публикация новой `SSTable` должна быть атомарной относительно `Get` и `Range`.

## Background compaction

Нужно добавить простую compaction для in-memory `SSTable`.

Коротко про идею:
- `flush` переносит данные из immutable memtable в **новую** `SSTable`, поэтому число `SSTable` со временем растет.
- `compaction` сливает уже существующие `SSTable` между собой, поэтому число таблиц уменьшается.
- Цель compaction — сохранить ту же видимую картину данных для `Get/Range`, но упростить структуру хранения.
- Публикация результата compaction должна быть атомарной: читатель видит либо состояние **до** слияния, либо **после**, но не частичный промежуточный вариант.

### Когда запускать compaction

- Если количество `sstables` становится **строго больше** `SSTableCompactThreshold`, compaction должна **рано или поздно** запуститься.
- Если после одного слияния таблиц все еще слишком много, compactor может запускать следующее слияние, пока число таблиц не станет приемлемым.

### Что именно нужно сливать

В этом ДЗ compaction быть специально упрощена (относительно реальных реализаций LSM):
- compactor всегда берет **две самые старые** `SSTable`
- compactor сливает их в **одну** новую `SSTable`
- новая таблица занимает место этих двух старых таблиц в логическом порядке версий

Это упрощение важно: не нужно реализовывать многоуровневую LSM и не нужно сливать все таблицы сразу.

### Правила слияния

- Compaction выполняется **одной** фоновой горутиной.
- Одновременно не должно выполняться более одной compaction.
- Результирующая `SSTable` должна быть отсортирована по ключу.
- Если один и тот же ключ есть в обеих сливаемых таблицах, в результате должна остаться **более новая** версия ключа (то есть версия из менее старой из этих двух таблиц).
- В базовом решении разрешается **сохранять tombstone** в результирующей таблице.
- **Бонус:** можно физически удалять tombstone при compaction двух самых старых таблиц, если вы корректно обосновали, почему это безопасно.

### Публикация результата compaction

- Пока compaction строит новую таблицу, старые `SSTable` должны оставаться видимыми для `Get` и `Range`.
- После завершения compaction новая `SSTable` должна быть опубликована **атомарно**.
- После публикации результата две старые `SSTable`, участвовавшие в compaction, должны исчезнуть из активного списка.
- `Get` и `Range` не должны видеть состояние, в котором старые таблицы уже убраны, а новая еще не опубликована.
- `Put/Delete` не должны блокироваться на всю длительность compaction; допускаются только короткие критические секции при публикации нового списка `sstables`.

## Close

- `Close()` переводит базу в состояние `closed`.
- После `Close()` вызовы `Put/Get/Delete/Range` должны приводить к `panic`.
- Если `Close()` выполняется параллельно с операциями, допускается завершение операций, начатых до установки признака `closed`; все операции, начатые после этого признака, должны `panic`.
- `Close()` должен:
    - если mutable memtable не пустая, перевести ее в immutable
    - дождаться `flush` всех immutable memtable
    - корректно остановить compactor
    - дождаться завершения уже начатой compaction
- После `Close()` не должно оставаться фоновых горутин.
- После `Close()` база не обязана специально «дожимать» compaction до порога; важно корректно завершить уже начатую работу и не потерять данные.

## Потокобезопасность

- Все операции безопасны при одновременных вызовах из нескольких горутин.
- `-race` не должен находить гонки.
- Ротация memtable атомарна относительно `Get/Put/Delete/Range`.
- Публикация результата `flush` атомарна относительно `Get/Range`.
- Публикация результата compaction атомарна относительно `Get/Range`.
- Нельзя вызывать пользовательский `fn` из `Range` под глобальным lock базы.

## Юнит-тесты — минимальный набор

Добавь минимум **4 новых** юнит-теста, например:
- `Range` возвращает ключи по возрастанию по всей DB.
- `Range` не возвращает tombstone и не возвращает дубликаты ключей.
- Более новое значение из `mutable` или `immutable` перекрывает старое значение из `sstable`.
- `Range` корректно работает по ключам, которые уже ушли в `sstable`.
- После compaction старые две таблицы заменяются одной новой без потери актуальных значений.
- `Range` корректно прекращается, если `fn` вернула `false`.
- `Close()` останавливает и flusher, и compactor.

## Стресс-тест

Напиши стресс-тест с множеством горутин:
- небольшое значение `MemtableMaxRecords`
- маленький `SSTableCompactThreshold`
- частые `flush` и compaction
- одновременные `Put/Delete/Get/Range`
- запуск под `-race`

Запускай так:
- `go test ./...`
- `go test ./... -run TestStress -race -count=1`

Хорошая идея для стресс-теста — держать рядом простую эталонную модель под `mutex` и время от времени сравнивать результаты `Get`. Для `Range` можно проверять хотя бы базовые инварианты: порядок ключей, отсутствие дубликатов и отсутствие значений для удаленных ключей.

## Подсказки

- Используй только стандартные библиотеки Go.
- Для построения `SSTable` используй `Range()` у immutable memtable — он уже должен идти по ключам в порядке возрастания и включать tombstone-записи.
- Для поиска по `SSTable` допускается линейный или бинарный поиск.
- Самая простая корректная реализация `DB.Range()` такая:
    1. под lock снять снимок ссылок на `mutable`, `immutable` и `sstables`
    2. вне lock пройти источники от новых к старым
    3. для каждого ключа запомнить первую встретившуюся версию
    4. отфильтровать tombstone
    5. отсортировать ключи
    6. вызвать `fn`
- Такая реализация не самая эффективная, но для этого ДЗ она допустима.
- Compaction тоже можно сначала сделать простой: собрать результат во временный срез, а потом одной короткой критической секцией опубликовать новый список `sstables`.
- Главное в этом ДЗ — **корректность и потокобезопасность**, а не максимальная производительность.

## Расшифровка критериев

### Корректность базового API и `Range`
- `Put/Get/Delete` работают по описанию.
- Tombstone корректно скрывает значение.
- `Get` возвращает копию `[]byte`.
- `Range` возвращает только видимые ключи, в отсортированном порядке, без дубликатов.

### Ротация memtable и `flush`
- Ротация происходит при достижении `MemtableMaxRecords`.
- Immutable memtable попадает в очередь `flush`.
- После `flush` появляется новая `SSTable`.
- Нет окна, в котором данные исчезают между immutable memtable и `SSTable`.

### Compaction
- Compaction запускается при превышении порога.
- Сливаются две самые старые `SSTable`.
- Более новая версия ключа перекрывает более старую в пределах compaction.
- После публикации результата старые таблицы исчезают из активного списка.

### Потокобезопасность
- `go test -race` без гонок.
- `Close()` корректно останавливает воркеры и не оставляет горутин.
- `Get` и `Range` не видят частично опубликованное состояние.

### Тесты и качество кода
- Добавлены минимум 4 юнит-теста по ТЗ.
- Есть стресс-тест, запускается под `-race`.
- Код понятно структурирован и читается.
